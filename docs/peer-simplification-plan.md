# Peer Coworkers 精简实施计划

日期 2026-11-09。用户要求由 GPT-6.1 Sol high 在新对话实施，可使用 peer。目标是通用、容易调用和维护的独立 CLI 协作工具，重点裁剪过重的轮次、交付及权限协议。

## 目标与判断

一次工作包应容易理解为提交任务、观察进展、读取交付、反馈或结束。实现、研究、审查共享这一流程，领域要求由具体任务提供。避免把 AIHDW、电路设计或当前模型分工写成通用工具的业务逻辑。

本轮需要实际删除或合并冗余流程及文档。增加一层包装但保留全部旧流程，不能算完成精简。衡量主要看调用步骤、worker 要遵守的规则、状态分支和重复代码，代码行数用于辅助核对。

## 已知起点

- 计划制定时，源码仓库 main 比 origin/main 多一个提交，另有多项未提交修复和未跟踪的 `followups.py`。先检查当前状态并保存可恢复基线，保留既有工作。
- 本轮只读比较的 27 个源文件中有 11 个与当前使用的技能安装版不同，需要重新核实。
- 源码版有独立审查结论和长报告支持，安装版另有完整差异检查、未验收交付关闭保护等修复。逐项取舍合并，不能直接选一侧覆盖。
- 快速入门仍写默认 600 秒，当前工具实际默认 2700 秒。更新有效文档时消除这类漂移，历史证据保留原貌。
- 近期修复涉及 agy 编辑和创建卡、命令折行与空行、外部文件读取、Cursor 信任与回复排队、`~/` 路径、提交不确定恢复。服务端 503 和网络问题也出现过。

## 第一阶段：确定唯一维护版本

审阅源仓和安装差异，区分实际缺陷修补、尚未发布功能及可裁剪协议。用简短清单记录取舍，把需要保留的能力收敛到源码仓库。检查正在运行的 peer，协调原修复对话，避免两个对话同时改同一工具或在运行中更换依赖。

继续使用现有安装器的备份和安装机制。发布后核对源码与安装物一致，并提供轻量版本或内容指纹，便于定位实际执行版本。无需新增发布服务。

## 第二阶段：裁剪 worker 合同和轮次

优先采用一份任务说明、一个产物或报告入口，以及工具维护的最少运行状态。任务说明先写目标、已知输入、写入范围、验收条件和交付位置。固定操作说明只保留实际需要的内容。

重点审查并删除或收回工具内部的内容包括：

- worker 手写 task/attempt/round 多重身份，强制 READY 文件和固定六数组 JSON 的负担。
- 常规反馈必须同时归档多类控制文件、推进多项状态、遵守固定回复次数的流程。
- 为交付摘要的长度、字段数量和格式发生反复返工的路径。
- 各文档和提示词重复叙述同一套协议。

优先让工具绑定任务身份和当前交付，让 worker 提交简短完成情况与证据。长报告使用普通文件。审查是否完成与被审产物是否通过应清楚表达，采用最小表示即可。需要区分旧结果和新反馈时，由工具维护一个最小关联标记，具体设计由实施者结合代码决定。

保留防止读取旧交付、重复发送和重复执行所需的最少事实。历史运行记录可以继续读取和收集，必要时提供小范围兼容读取；已有活动任务结束后再切换安装，避免双套运行协议长期并存。

## 第三阶段：减少权限和交互重复

任务写入范围清楚表达，CLI 原有 sandbox、审批及账号设置继续起作用。精简重复的角色写入矩阵、状态门槛及手动参数，让通用任务能正常写报告和必要的临时产物。

审批操作保留当前会话、实际动作、准确路径及单次发送的对应关系。审查是否可以减少整屏装饰、动画、折行等无关变化对识别的影响，复用已有解析逻辑，避免每个显示差异都新增完整流程。

提交、回复或审批发送结果不明确时，先核对实际回执及产物。不要自动补 Enter。未知或内容不完整的审批继续明确报告。权限精简不能通过关闭 CLI sandbox、修改全局权限或普遍自动批准实现。

基于现有观察结果直接展示当前状态和需要处理的动作，减少监督者重复读屏。故障信息区分容量、网络、审批、交付和工具错误即可。重试必须考虑是否已产生副作用，避免引入新的通用调度器或复杂重试框架。

## 第四阶段：真实使用、发布和汇报

使用本轮实际工作验证流程。可以把一个边界明确的实现包交给 agy，把最终通用性和精简效果审查交给 Cursor。监督者负责集成和独立检查，控制同一文件的写入归属。工具自身改动期间，已启动的 peer 使用固定版本，安装发布在有关会话结束后进行。

用户偏好 agy 的 `gemini-3.8-flash-high`、Cursor 的 `cursor-grok-4.6-xhigh`，均使用标准速度，实际模型和档位仍需核对。若 CLI 或模型不可用，保留故障证据，监督者继续可独立完成的部分。无需为增加调用次数拆分小型强耦合改动。

验证覆盖真实提交、读取产物、一次实际反馈、审查发现问题后的交付及结束清理。只对本轮改变的故障路径使用已有真实画面做定向回放。遵守仓库规定，不使用冒烟测试，不新增持久化测试代码或 fixtures，临时验证脚本用完删除。不能把模拟回放描述成真实 CLI 验收。

完成时交付：

- 经精简并已安装的通用 peer 工具，源码与安装版一致。
- 更新后的简短 SKILL、快速入门和必要命令说明，删除失效的协议说明。
- 一份短评估，说明删掉了哪些步骤和状态、保留什么及原因，并列出真实任务验证和未验证部分。
- 本轮相关 Git 提交与清晰的工作区状态。提交前区分本轮范围和已有无关改动。远端推送遵循当前仓库的明确授权。

## 协调与执行约束

用户已授权直接推进，无需常规确认。常规实现选择由 Sol high 判断。先修实际问题，再精简到可维护的最小方案；不增设仪表盘、调度平台、插件框架或电路专用逻辑。

用户已授权向原 peer 修复对话反馈调用故障，并在获知修复后重试。实施者接手前应告知统一写入归属，需要对方排障时协调具体文件，避免同时修改。具体对话标识保存在本地交接记录。

沿用用户此前要求的目标模式推进。完成或约两小时的可交接节点时，保存当前状态并向原监督对话汇报已完成内容、证据、剩余事项及活动 peer。新对话必须携带用户关于回报和故障反馈的授权上下文。

任务完成或出现无法自行解决的阻塞，按用户已授权的通知规则发送一次结果。收件信息保存在本地交接记录。
