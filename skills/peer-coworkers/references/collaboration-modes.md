# 协作模式

从用户的 peer_coworkers 提取角色与验收规则，取消 Luna/DeepSeek 身份 allowlist 和固定模型路由。这里的工作进程均通过独立 CLI 会话运行。

| 需求 | 模式 | 输入边界与验收 |
|---|---|---|
| 攻击已有改动中的具体故障路径 | 定向攻击审查 | 给出故障假设、完整调用链和合同；发现需定位或复现 |
| 问题存在多个合理方案 | 独立求解 | 两个新上下文先只看原始问题；用可验证证据比较方案 |
| 实现与针对性测试可独立分工 | 实现 / 测试 | 明确各自归属；确认测试能识别目标故障；不得同时写共享工作区 |
| 架构或工具选择未定 | 提案 / 批评 | 先形成提案再批评，需求稳定后另建实现包 |
| 实现已形成，需要独立视角 | 实现 / 审查 | 审查者看最终产物与合同，不看实现者自评；主代理裁决 |
| 接口稳定，工作流相互独立 | 并行拆分 | 每条写入流独立 worktree、归属和验收；串行集成 |

首选最小有效分工：主代理加一个有界工作进程。只读工作流可以并行，前提是共享材料不再被写入。相互依赖的实现、审查、修复串行执行。任务工具不创建 worktree 或自动合并，不允许工作进程代做分派。

角色确定后按 [模型能力与选型](model-selection.md) 分配 CLI、具体模型与已确认档位。独立求解/审查优先考虑另一模型家族；全用同一模型可以有合理任务或资源原因，但应在首次派工时说明。不同 CLI、Auto、同家族不同版本都不能直接证明模型视角多样性，不按模型票数代替主代理验收。

一个工作包最多一次广泛审查、一次定向修复、一次增量复核。新缺陷需要广泛重理解、重写或改变需求时重新分包。独立最终检查按风险选择：中高风险且会改变授权、发布、完整性或生命周期条件时保留新上下文检查。主代理验证每项实质发现；零发现只说明没有产出发现。

涉及授权或生命周期的包，需要在验收条件中写明：谁能授权、绑定哪个产物和版本、前后状态、前置条件、过期/重放行为，以及缺失或矛盾证据时的处理。外部负责人的决定不能由模型推断；未验证的决定不视为已获授权。
